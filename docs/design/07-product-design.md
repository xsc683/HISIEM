# Phase 4 产品设计 — 用户接入与解析规则管理(SIEM 产品化)

> 状态:产品设计稿 · 2026-08-16
> 本文档是**产品层**设计(用户角色、体验流程、功能模块、竞品对标),与 [06-user-onboarding.md](06-user-onboarding.md) 的**技术层**设计互补。
> 参考业界成功产品在"日志接入 / 解析规则管理"上的产品与 UX 模式。

## 1. 产品定位

**一句话定位**:HISIEM 是一个轻量级 SIEM,本文档设计其**管理控制台**——让安全工程师能自助地把新日志源接入系统、管理解析规则,而不是改配置文件。

**解决的核心问题**:
- 现在加一个数据源 = 手改 `logstash.conf`(grok 模式/ECS 字段/时间解析)→ 门槛高、不可复用、无测试、无监控。
- 产品目标是:把"接入日志"从**改配置**变成**点几下**。

**产品形态**:Web 管理控制台(与 Kibana 检测看板分工:控制台管"接入和规则",Kibana 管"检测和告警")。

## 2. 目标用户与角色(personas)

| 角色 | 典型诉求 | 高频操作 | 关注点 |
| --- | --- | --- | --- |
| **安全管理员** | 快速把新日志源接进来 | 接入数据源、选/建解析模板 | 省事、可复用、不出错 |
| **运维/采集工程师** | 部署采集端点、确认日志进来了 | 配置采集、看数据是否流入 | 连通性、失败率 |
| **安全分析师** | (主要用检测/告警,接入层次要) | 偶尔看数据源健康、报解析问题 | 数据完整、不丢日志 |

> 设计取舍:**接入层面向"管理员/运维"**,不做分析师那套告警调查(那是 Kibana + 检测层的活)。

## 3. 竞品对标(产品 / UX 层面)

| 产品 | 接入与解析的产品做法 | 借鉴点 |
| --- | --- | --- |
| **Splunk** | `Add Data` 向导(选择数据源类型 → 上传/配置 → 识别 sourcetype);`sourcetype` 是解析的"钥匙",字段提取在 search-time 配置 | **向导式接入**;解析按"源类型"组织 |
| **QRadar** | `Log Source` 管理(加日志源 → 选 DSM → 自动识别);**DSM Editor 基于样例事件可视化提取字段**(粘贴日志 → 定义字段 → 看结果) | **自动识别日志源**;基于样例的可视化字段提取 |
| **Elastic** | Fleet + **Integrations 市场**(选集成包 → 部署 Agent → 自动采集解析);`Custom Logs` 支持自定义 | **模板/集成市场**;打包化"选即用" |
| **Cribl** | **Onboarding 流程**(选 Pack → 样例测试 → 路由);**unknown 桶兜底**(未知格式不丢,事后补解析);数据源文档化;健康监控 | **样例测试**;未知兜底;数据源文档化+监控 |
| **Sentinel** | **Data Collection Rule(DCR)**:声明式"表 + 解析 + 转换" | 声明式接入规则 |

**提炼的产品 UX 共性**(本产品遵循):
1. **向导式接入**:选类型 → 配置端点 → 测试 → 生效,而不是填表单/改配置
2. **模板/规则库**:预置解析器,用户"选"而非"写"
3. **基于样例的即时反馈**:粘贴一条日志 → 立刻看到提取的字段
4. **未知兜底**:解析失败的日志进 raw 桶,可事后补规则,不静默丢
5. **数据源文档化 + 健康监控**:每个源有元信息,失败率/量可见

## 4. 核心用户旅程(UX flows)

### 4.1 接入一个数据源(主旅程)

```
① 新建数据源      ② 选解析模板       ③ 配置采集端点     ④ 发样例验证       ⑤ 生效
"接入中心"新建  从模板库选/检索  填端口/路径/IP/名称  粘贴样例→看字段预览  点"生效"
   │               │                 │              │                  │
   │            (没有合适的?→        │          (字段对→下一步;   生成配置→同步
   │             跳去自定义解析)      │           不对→回模板库换)   →日志流入→确认
   └──────────────────────────────────┴──────────────────────────────┘
```

**每一步的交互反馈**:向导右侧常驻"字段预览"面板;生效后跳转到该数据源的健康页(最近 1 小时事件量、解析失败率)。

### 4.2 自定义解析规则(次旅程)

```
① 入口:模板库找不到 → "自定义解析"
② 粘贴一条样例日志
③ 编写/微调 grok 模式(自动补常用模式片段,实时校验)
④ 即时预览:提取字段 + 解析成功/失败
⑤ 补 ECS 字段/actions(成功/失败等)→ 填正负样本
⑥ 保存为模板(experimental)→ 可复用
```

### 4.3 数据源健康监控

- 每个数据源:最近事件量、解析失败率、最后收到时间
- 失败率突升 → 高亮告警(可能模板变了/格式改了)
- 未知/解析失败日志可下钻查看原始内容,决定"补模板"还是"该源下线"

## 5. 产品信息架构(功能模块)

```
管理控制台
├── 接入中心          ← 新建数据源(向导)、我的数据源列表
├── 解析规则库        ← 预置模板浏览/检索、自定义解析、模板详情/测试
├── 数据源管理        ← 数据源 CRUD、采集端点、关联模板
├── 数据健康          ← 各源事件量/失败率/未知日志、趋势
└── 设置              ← 资产关键度、ES/存储状态、(后续)用户与权限
```

## 6. 功能能力地图 + MVP 优先级

| 模块 | 能力 | 优先级 |
| --- | --- | --- |
| 接入中心 | 数据源向导(选模板/配端点/测试/生效) | **MVP** |
| 接入中心 | 数据源落库 + 生效到 Logstash | **MVP** |
| 解析规则库 | 预置模板浏览/选择 | **MVP** |
| 解析规则库 | 自定义解析(样例 → grok → 预览 → 保存) | P1 |
| 数据源管理 | 数据源 CRUD、状态 | P1 |
| 数据健康 | 事件量/失败率/未知日志视图 | P1 |
| 设置 | 资产关键度配置 | P2 |
| 设置 | 用户与权限(RBAC) | P2 |

**MVP 定义**:安全管理员能用向导把一种新日志源接进来并真正生效(日志流入可查),且能从模板库选到 SSH 等预置模板。

## 7. 产品形态与演化

- **当前**:Web 控制台(React) + Spring Boot API;接入层独立于 Kibana。
- **后续**:API 开放(第三方/脚本接入)、与 Kibana 检测看板导航打通。
- **与检测层分工**:控制台管"数据进得来、解析对不对";Kibana/告警管"检测得准不准、处置得完不完"。
