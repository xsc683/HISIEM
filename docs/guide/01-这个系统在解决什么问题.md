# 这个系统在解决什么问题

> **读者对象**：第一次接触本仓库的人——产品、测试、运维，或刚接手这段代码的工程师。
> **前置**：不需要预先了解 Kafka、Flink 或 Elasticsearch。本篇一个技术组件都不展开，需要的前提只有一条——知道"服务器会往日志文件里写东西"。

---

## 1. 一个具体的早上

先不讲架构，讲一个场景。

某公司有一批 Linux 服务器、网络设备和业务应用，它们一天 24 小时都在往日志里写东西：谁登录了、谁登录失败了、哪个服务重启了、哪个定时任务报错了。这些日志被集中收进一个平台。

安全团队的成员周一早上到岗，面对的是过去 24 小时的全部日志。其中绝大多数是正常的——有人正常登录，服务正常重启，定时任务正常重试失败。真正需要人介入的事件，可能是当天个位数。

于是问题不是"日志太多"。把日志删掉一半并不能让人更快发现攻击。真正的问题是：

> 面对持续不断的海量安全事件流，**哪些重要，接下来应该发生什么？**

这句话是本仓库 README 开篇给出的定义，也是整个系统的目的。它听起来像一句话，拆开却是四件互相独立的难事（下面四条同样来自 README 的概括，我用工程语言重述）：

1. **把事件接进来并标准化。** 不同厂商、不同格式的日志必须进入同一份 schema。关键在于后半句：**无法解析的记录不能静默消失**——一条解析失败但被丢掉的日志，等于一次已经发生的漏报，而且没人知道。
2. **在不可靠的事件流上实时检测。** 日志会延迟到达、会乱序到达、会突然爆发。如果检测逻辑假设输入是有序、完整、准时的，它会同时产生两种错误：漏掉真正的攻击，和重复报告同一次攻击。
3. **在重放下保持结果稳定。** 流式管道会失败并重启，这是常态而不是事故。重启之后不能重复计数、不能重复告警、不能丢状态。
4. **把一条告警变成可审计的动作。** 响应不是给某个地址发一个 webhook。它是一条带租约、带审批、带分支、带重试的工作流——因为响应动作会真的改变生产环境。

把上面四条记在心里，后面几乎所有"为什么这么设计"的疑问都能自己回答。它们不是功能清单，而是这个仓库设计决策的来源。

## 2. SIEM 在本项目的定义

**SIEM** 是 Security Information and Event Management 的缩写。这个长名字其实说了两件事，各对应一条腿：

| 词 | 对应的事 |
| --- | --- |
| Information | 把分散在各处的信息**收集起来并标准化**——采集、解析、统一字段 |
| Event Management | 在**事件流上做出判断并处置**——检测、告警、调查、响应 |

只做前一半，得到的是一个日志搜索工具；只做后一半，没有可靠的数据可用。本项目的定义是两者的合体：

> 基于 **Elastic Stack + Kafka + Flink** 的轻量级 SIEM 平台，控制面由 **Spring Boot** 承载；覆盖日志采集、解析与标准化、实时检测、告警存储、分析员控制台和确定性 SOAR 响应执行。

还有一条容易被误读的定位，值得单独说清楚：**这刻意不是一个 AI 项目**。它是一个流式数据平台，以及由此带来的可靠性、一致性和运维问题。消费它的 AI 调查层是**另一个独立系统**，不在本仓库里（见 [03-从告警到处置决策.md](03-从告警到处置决策.md)）。

"轻量级"三个字也要当真：本仓的规则集是演示集，不是生产检测内容库；生产安全加固（TLS、认证、高可用）是已文档化的门禁，而不是已经交付的默认值。当前边界以 [`../current-status.md`](../current-status.md) 为准。

## 3. 称谓链：从"一行文本"到"一次处置"

这个系统里，同一条安全事实在不同阶段有不同称谓。混用称谓是新手最容易踩的坑——说"日志"的时候可能指设备吐出的一行字，也可能指 Elasticsearch 里的一条文档，而这两件事的处理方式完全不同。

| 称谓 | 准确含义 | 谁产生它 | 它落在哪 |
| --- | --- | --- | --- |
| **日志** | 设备吐出的一行原始文本 | 数据源自身 | 还没进系统 |
| **事件** | 解析成功、字段已按 ECS 标准归一化的一条结构化记录 | Logstash | Elasticsearch 事件索引；同时进 Kafka |
| **命中** | 一条事件满足了某条规则的条件 | Flink 的规则求值 | 不单独落库；它是"事件 → 告警"的中间动作，可按规则反查 |
| **告警** | 命中后落库的、可被处置的对象，带规则元数据与严重级 | Flink | Elasticsearch 告警索引 |
| **案件** | 围绕一个实体把多条告警聚成的调查单元 | 自动聚合任务，或分析师手动建立 | PostgreSQL 为事实源，Elasticsearch 保留兼容镜像 |
| **处置** | 对告警/案件的状态判定（verdict）与响应执行 | 分析师，或 SOAR 运行时 | 控制面数据库 |

从这张表里能读出三件事：

1. **每一级都有明确的产生者**，不存在"平台自己产生了什么"这种模糊说法。定位问题时，"这一步是谁做的"永远可以回答。
2. **一次命中产生一条告警，而不是一次攻击产生一条告警。** 同一条事件命中多条规则，就会产生多条告警——这个现象在 [02](02-一条日志的完整旅程.md) 里有完整的例子，它经常让第一次看数据的人困惑。
3. **实体是贯穿全链的关联键。** 告警和案件都挂在某个实体上（优先 `source.ip`，其次是 `user.name` / `host.name`）。这是"同一个攻击者的多条告警能被聚到一个案件里"的前提。稳定的对象标识与关联规则以 [`../product-contract.md`](../product-contract.md) 为准。

## 4. 时间不止一个

在安全系统里，"时间"是最容易出错的地方，因为这个系统里同时存在三种时间，而它们经常被含糊地统称为"平台时间"：

| 时间 | 含义 | 谁决定它 |
| --- | --- | --- |
| **事件时间** | 日志里写的、事情真正发生的时间 | Logstash 从日志文本里解析出来 |
| **告警生成时间** | 系统处理并产出这条告警的时间 | 检测环节在写入告警时打上 |
| **显示时间** | 你在页面上看到的时区 | 前端渲染；而原始 JSON 用 UTC |

为什么必须分清：检测用的是**事件时间**——因为一个攻击行为是否成立，取决于事件发生的先后，而不是它们被系统读到的先后。而带时间窗口的规则，其告警上的时间字段表示的是**窗口结束时间**，不是某一条事件的时间。同一个字段名在不同规则类型下含义不同，这就要求看数据的人先知道这条告警是谁产生的。

本篇不展开各时间字段的精确语义和存储类型；确认时以 [`../product-contract.md`](../product-contract.md) 的验收项和 [`../event-alert-schema.md`](../event-alert-schema.md) 为准。

## 5. 为什么要把系统切成两个平面

本项目的架构分成两条链路（见 [`../architecture.md`](../architecture.md)）：

```text
数据面    Logstash → Kafka → Flink → Elasticsearch
         （吞吐、事件时间、窗口、检测）

控制面    Spring Boot → PostgreSQL
         （事务、案件、规则、IAM、SOAR、运维）
```

分开的理由不是"技术上更时髦"，而是**两个平面的正确性要求不一样**：

- 数据面针对**事件时间流式处理与收敛**优化。它面对的是高速、乱序、必然重放的数据流，追求的是"最终结果正确"，而不是"每一步都原子"。
- 控制面针对**事务状态与引用完整性**优化。它面对的是用户在页面上的操作，追求的是"这个状态变更要么全成要么全不成"。

两个平面在一个刻意的边界相遇。这个边界有一条明确的规则：**控制面不参与实时日志消费，也不把事件和告警的正文复制到 PostgreSQL**。控制面检索事件和告警时，是去 Elasticsearch 查的。

而系统中最有意思的一致性问题就出在边界上：**一个案件可以同时跨 Elasticsearch 和 PostgreSQL**。案件的事实源在 PostgreSQL，但页面上要展示的告警和事件在 Elasticsearch 里。数据面与控制面之间、以及 PostgreSQL、Elasticsearch、Kafka 三者之间**没有分布式事务**——跨系统的收敛靠 outbox 模式和定时对账，而不是靠一次提交。

这个取舍的后果贯穿整个仓库，也是读代码时最值得留意的部分。

## 6. 失败是设计的一部分

一个只在理想输入下正确的安全系统是没有价值的，因为它的输入从来不理想。本仓对失败的处理有一条统一的取向：**明确失败优于静默降级**。

最直观的体现是数据面上**两个不同的失败出口**：

| 出口 | 接收什么 | 为什么在这里 |
| --- | --- | --- |
| 原始隔离索引（`*raw*`） | Logstash 解析或时间解析失败的记录 | 这类记录**根本不会进入 Kafka**，因此不会进入检测链路。它们被留在可查的地方，而不是被丢弃 |
| 解析死信 topic（DLQ） | 已经进了 Kafka，但 Flink 无法解析 JSON 或事件时间的消息 | 这类记录已经到了检测引擎门口，被单独隔离，而不是让作业反复重启 |

这两个出口守的是两个**不同的边界**，所以是两个不同的失败出口，不能合并成一个。

同样的取向也出现在别处：检测规则在作业启动时会用一个运行时清单校验规则目录，**不匹配是启动失败，而不是静默地换了一套检测规则**。含义很直接——宁可让系统响亮地停下来，也不要让它悄悄按另一套规则运行，因为没人会注意到后者。

## 7. 这个系统现在做到哪一步

本仓对状态的表述是刻意保守的。一句话结论是：

> HISIEM 已完成检测链路、控制面、接入向导、告警处置、调查台、生命周期驱动的 SOAR MVP 和运行态扫描主要闭环，可以作为开发/演示环境使用；**生产级部署仍需完成数据面安全加固、高可用和跨存储一致性治理**。

把它翻译成阅读建议：

- 你在读的是**一套已经跑通的开发/演示环境实现**，不是设想稿。数据链路、控制面、前端、运行态扫描都有对应的验证记录。
- 同时有六类**已登记但未闭环的生产风险**（数据面安全、案件镜像收敛、后台任务重放、多租户隔离、容量与灾备、lifecycle 投递的重复窗口）。这些不阻塞使用，但每一项都写在明处。
- 完整清单与事实来源见 [`../current-status.md`](../current-status.md)。

本篇和接下来三篇讲的都是**当前实现**，不是目标方案。如果你在某处读到一个能力描述，想知道它是否已经交付，判断顺序是：先看 `current-status.md`，再看 `product-contract.md`，最后回到代码。
