# 想深入读哪一篇

> **读者对象**：读完本目录前三篇、准备往某个方向深入的人；也适合作为交给新人的"文档地图"。
> **前置**：无。这份文档不讲系统，只讲"本仓的文档分别是什么、该按什么顺序读、什么问题该去问哪一份"。

---

## 1. 这份文档解决什么问题

本仓的文档不是按一套统一结构写的，它们是在不同阶段、为不同目的写的，因此**权威性、时效性和抽象层级都不同**。拿错了文档，你会得到一份技术上正确、但已经不是当前事实的答案。

这份文档做三件事：

1. 说明每一类文档的**定位**（它回答什么问题、不回答什么问题）。
2. 说明它们之间的**先后关系**（谁覆盖谁、冲突时信谁）。
3. 给一张"我想了解 X → 读哪份"的对照表。

## 2. 先分清这些文档的层次

```text
本项目入门   docs/guide/            ← 你正在读的地方：项目优先，先讲问题再讲技术
概念基础     docs/learn/            技术优先，先讲组件原理再对回本项目
当前事实     README.md / docs/README.md / current-status.md
             architecture.md / product-contract.md / roadmap.md / project-progress.md
操作交付     docs/deployment.md / docs/operations.md
技术参考     docs/design-decisions.md / event-alert-schema.md / rule-engine.md / soar.md
             docs/design/**（专项）
代码级走读   docs/architecture-analysis/**
面试材料     docs/interview/INTERVIEW_GUIDE.md

```

### 2.1 `docs/guide/`（本目录）——项目优先的入门

定位：**先讲这个系统在解决什么问题，再讲它怎么运转**。适合"我刚拿到这个仓库，想先建立心智模型"。

本目录与 `docs/learn/` **不重复**，这是刻意的分工：

| | 先讲什么 | 适合什么时候读 |
| --- | --- | --- |
| **本目录** | 问题 → 一条日志的旅程 → 告警之后 → 地图 | 你还不了解这个项目，读技术名词会失去上下文 |
| **`docs/learn/`** | 概念定义 → 场景举例 → 本项目对应 | 你已经知道项目在做什么，想理解某个组件为什么这样用 |

`docs/learn/` 的推荐顺序是"SIEM 基础 → 全链路 → Kafka → Elasticsearch → Flink → Logstash"，每篇按"定义 / 为什么需要 / 核心概念 / 本项目对应 / 常见问题 / 动手验证 / 自测"组织。它是**学习材料，不替代代码、`infra/` 配置或产品契约**。

**本目录的索引状态**：`docs/guide/` 已登记进 [`../README.md`](../README.md) 的「入门材料」一节，四篇与推荐顺序都在那里，从文档中心进来可以直接看到。

### 2.2 `docs/design/`——专项参考，不是架构副本

`docs/design/` 只放**独立的专项参考**：某个子系统的实现边界、某个领域的覆盖情况、某项加固的门禁。它**不再存放按阶段复制的架构、产品或路线图长文档**。

使用它时有一条必须知道的规则：

> 专项文档如果描述"待实现"，必须同时在路线图里登记，**不能被当作现成功能**。

所以读到一份设计文档里说某个能力"将支持"，你的下一步是去 [`../roadmap.md`](../roadmap.md) 确认它是否已交付——而不是直接当成能用的东西。

### 2.3 `docs/architecture-analysis/`——代码级走读

这个目录里是逐层、逐子系统的实现级走读（从"分层架构与模块总览"到"Web 控制台与基础设施"，共 7 篇加一份目录说明）。

**一个值得知道的实情**：这个目录**没有出现在** [`../README.md`](../README.md) 或根 [`README.md`](../../README.md) 的索引里。它的定位与权威性以该目录自身的说明文件为准——本篇没有读它，因此不对其组织方式和时效性做判断。

### 2.4 `docs/interview/`——面试材料

本仓的面试入口是 [`../interview/INTERVIEW_GUIDE.md`](../interview/INTERVIEW_GUIDE.md)：自 30 秒介绍到深度追问，**每一条技术陈述都以本仓库实现为依据**，随产品演进，留在仓内。

注意：**跨项目的面试学习材料已于 2026-09-23 移出本仓库**，现位于独立资料库 `D:\Project\interview-prep\`。移出的原因是那批材料同时覆盖两个仓库，不属于任何一个产品仓，而且是个人学习材料而非产品文档——所以**不要在本仓找它**。

### 2.5 `docs/archive/`——历史，只用于追溯

归档内容**仅用于追溯，不作为开发入口**。规则很硬，值得全文引用：

> 归档内容可能包含当时已修复的问题或旧接口，**使用前必须回到[当前状态](../current-status.md)和代码确认**。

另外，原 `docs/story/story-01` 至 `story-10` 及模板**已全部删除**——因为它们重复 API、路由和状态，产生了多份互相矛盾的契约。当前接口统一以 [`../product-contract.md`](../product-contract.md) 为准；迁移说明见 `docs/story/README.md`。**如果你在别处看到一份 Story 文档的引用，那份文档很可能已经不存在了。**

## 3. 先后关系：冲突时信谁

事实来源有明确的优先级。本仓文档中心的阅读顺序是**"当前事实 → 产品契约 → 操作交付 → 技术参考 → 学习资料"**。落到具体冲突上：

| 冲突 | 信谁 |
| --- | --- |
| 代码/测试 与 任何文档 | **代码与测试**。接口变更必须先改代码测试，再同步文档 |
| `product-contract.md` 与 Story / 历史材料 | 产品契约 |
| `current-status.md` 与 设计文档里描述的"已实现" | 当前状态 |
| `roadmap.md` 与 设计文档里的"待实现" | 路线图（它决定那件事到底做没做） |
| `learn/` 学习材料 与 代码 / `infra/` / 产品契约 | 后者。学习材料允许保留简化示例 |
| `archive/` 与 任何其他文档 | 其他文档；归档只用于追溯 |

一句话记法：**跑得起来的代码 > 当前事实文档 > 产品契约 > 专项设计 > 学习材料 > 历史归档**。

## 6. 三条"不要从这里开始"

1. **不要从 `docs/archive/` 开始。** 它可能包含当时已修复的问题和旧接口，用它之前必须回到当前状态和代码确认。
2. **不要把 `docs/design/` 里的"待实现"当成现成功能。** 专项文档里的未来能力一定在路线图里有登记，两边对照着看。
3. **不要用 `docs/learn/` 替代代码和配置。** 学习材料允许保留简化示例，`infra/` 文件才是配置的唯一来源。

## 7. 改文档之前要知道的五条规则

本仓对文档有明确的变更规则。如果你打算**修改**文档（而不只是阅读），先看这五条：

1. **当前事实只写入** `current-status.md`、`architecture.md` 或 `product-contract.md`；`project-progress.md` 只做派生的管理视图和问题关闭登记。
2. **阶段计划只写入** `roadmap.md`；不再新增第二份路线图。
3. **接口、路由和验收只写入** `product-contract.md`，代码测试是最终验证。
4. **Schema 变更**要同步 `event-alert-schema.md`、mapping、生产端和测试。
5. **设计参考必须标明"已实现/待实现"**，不能用历史分析结论覆盖当前代码。

另外，`current-status.md` 自己还给出了六条"遇到某类问题该看哪份"的使用规则（现在是什么 / 怎么部署 / 为什么这样设计 / 怎么验收 / 怎么学习 / 历史证据）——它是本仓文档分工最凝练的一处表述，值得直接读一遍。

这几条规则解释了一个常见的困惑：为什么本仓的文档看起来"不敢把话说满"。因为每份文档都有它被允许断言的范围，超出范围的结论必须回到代码。
