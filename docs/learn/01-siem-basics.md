# 功课 1 — SIEM 是什么 + 事件→告警术语

> 目标:建立 SIEM 的"心智模型",把数据流里各个阶段的名词(日志/事件/告警/案件)和本项目一一对上。

## 1. SIEM 是什么

**全称**:Security Information and Event Management(安全信息与事件管理)。

**一句话**:给整个网络装"监控摄像头 + 值班保安"——把所有设备产生的日志收集起来,统一分析,发现可疑行为就报警。

**三个核心动作**:

```
采集(把日志收进来)→ 检测(判断有没有攻击)→ 告警(通知分析师)
```

**和普通日志系统/监控系统的区别**:

| | 普通日志系统(ELK) | 监控系统(Prometheus) | SIEM |
| --- | --- | --- | --- |
| 关心什么 | 日志能查到 | 指标是否正常 | **行为是否可疑** |
| 输出 | 日志/看板 | 指标/告警(阈值) | **安全告警(规则/关联/评分)** |
| 核心问题 | 发生了什么 | 系统坏了吗 | **被攻击了吗** |

本项目把 ELK 当"采集/存储底座",但**检测引擎(Flink)和告警模型才是 SIEM 的灵魂**。

## 2. 数据在 SIEM 里的"身份演变"(最重要的术语链)

一条安全数据从进来到被处理,形态不断变化,**每个阶段有专门的名字**:

```
日志 log → 事件 event → 检测命中 hit → 告警 alert → 案件 incident
```

| 阶段 | 是什么 | 在哪里发生(本项目) |
| --- | --- | --- |
| **日志 (log)** | 原始文本行,设备自己输出 | 还没进系统:`Aug 1 10:20:00 server03 sshd[9999]: Failed password for test from 172.16.1.20` |
| **事件 (event)** | 解析、结构化后的 JSON,带统一字段 | **Logstash**:grok 提取字段 + ECS 标准化 → 写入 `siem-events-*` |
| **检测命中 (hit/match)** | 某事件**满足某条规则的条件** | **Flink**:`DetectionFunction` 里 `rule.getCondition().matches(...)` 返回 true |
| **告警 (alert)** | 命中后生成的分析师可见记录 | **Flink** 生成告警 JSON → 写入 `siem-alerts` |
| **案件 (incident/case)** | 一个/多个告警归并后进入调查的单元 | 本项目**还没做**(未来 alert-service) |

> 关键理解:**一条日志可能产生 0 条、1 条或多条告警**。例:`Failed password for test` 同时满足"SSH 认证失败"和"常见弱账号"两条规则 → 一条事件 → **两条告警**。

## 3. 关键术语表

### 3.1 告警本身的属性

| 术语 | 定义 | 本项目例子 |
| --- | --- | --- |
| **severity(严重级)** | 告警的静态危险等级 | `alert.severity`:info/low/medium/high/critical |
| **risk_score(风险分)** | 数值化危险度(0-100),比 severity 更精细、可计算 | 设计 P0 要加的 `alert.risk_score` |
| **rule_id** | 命中哪条规则 | `rule-ssh-auth-failure-001` |

### 3.2 告警质量(判得准不准)

| 术语 | 定义 | 直观理解 |
| --- | --- | --- |
| **True Positive (TP)** | 告警了,确实有攻击 | 抓对了 |
| **False Positive (FP)** | 告警了,但其实是正常行为 | **误报**(报错了) |
| **False Negative (FN)** | 有攻击,但没告警 | **漏报**(没抓到) |
| **FP rate(误报率)** | FP / (FP + TP) | 100 条告警里有多少是误报 |

> 设计文档里"verdict 回流调优"就是在给每条告警打 TP/FP 标签,统计每条规则的误报率,把误报高的规则调掉——**目标:误报率降下去,同时不漏报**。

### 3.3 检测手段

| 术语 | 定义 | 本项目对应 |
| --- | --- | --- |
| **normalization(归一化)** | 把不同设备的字段统一成一套(如 `src_ip`→`source.ip`) | Logstash 的 ECS 标准化 |
| **correlation(关联)** | 把多个事件/信号组合起来判断 | 时间窗口规则、CEP 攻击链 |
| **suppression(抑制)** | 同一类告警在一定时间内只发一条 | 设计 P0:keyed state + TTL |
| **dedup(去重)** | 完全相同的告警只保留一条 | 与 suppression 配合 |
| **enrichment(富化)** | 给事件补充上下文(地理/IP 信誉) | 设计 P2:GeoIP |

### 3.4 时间

| 术语 | 定义 | 本项目 |
| --- | --- | --- |
| **event time(事件时间)** | 攻击实际发生的时间(日志里写的) | `@timestamp` = 日志时间(Logstash date filter 解析) |
| **ingest time(摄入时间)** | 系统处理到它的时间 | 单独存 `alert.created_at` |

> **这是本项目踩过的一个大坑**:`@timestamp` 必须用事件时间,不能用摄入时间,否则分析时序全乱。

### 3.5 组织与角色

| 术语 | 定义 |
| --- | --- |
| **SOC** | 安全运营中心,人(分析师)待的地方 |
| **SIEM** | 工具(给 SOC 用的"监控摄像头+保安") |
| **SOAR** | 自动化处置工具(封 IP/隔离机器),和 SIEM 配合 |
| **XDR** | 扩展检测响应,更大范围的检测(SIEM 的下一代概念之一) |

### 3.6 效率指标

| 术语 | 定义 |
| --- | --- |
| **MTTD** | 平均检测时间(攻击发生到被系统发现) |
| **MTTA** | 平均确认时间(发现到分析师确认) |
| **MTTR** | 平均修复时间(确认到处置完成) |

## 4. 术语链 × 本项目组件总览

```
日志 ──Logstash──> 事件 ──Flink──> 命中 ──> 告警 ──ES/Kibana──> 分析师看到
  (log)          (event)          (hit)       (alert)             ↑
                                    │                            │
                                    命中了哪条规则?          future: incident
                                    rule_id                  (案件,未做)
```

## 5. 自测

1. "一条日志最多产生几条告警?"—— 取决于命中几条规则(本项目实例:最多 2 条,见 §2)。
2. "`@timestamp` 是事件时间还是摄入时间?"—— 事件时间。
3. "误报率 FP rate 高了,应该做什么?"—— 调规则/退役规则,而不是假装没看见。
4. "SIEM 和 ELK 的区别?"—— ELK 是存储检索底座,SIEM 多了检测引擎 + 告警治理。
