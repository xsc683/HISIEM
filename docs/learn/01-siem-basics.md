# 功课 1 — SIEM 基础概念与「事件 → 告警」术语链

> 本文档建立 SIEM 的基础心智模型,并给出安全数据在管道各阶段的准确称谓及其在本项目中的对应。阅读本系列前,建议先跑通本项目部署并发送过一条测试日志(见 `docs/deployment.md`)。

## 1. SIEM 的定义与定位

**定义**:SIEM(Security Information and Event Management,安全信息与事件管理)是一类安全平台,负责对网络基础设施产生的安全日志进行**集中采集、归一化、实时检测与告警**,为安全运营提供统一的分析与响应入口。

**三个核心功能**:

| 功能 | 说明 |
| --- | --- |
| 采集(Security Information) | 集中收集各类设备(服务器、网络设备、应用)的安全日志 |
| 分析与检测(Event Management) | 对事件做字段归一化、关联、规则匹配与评分 |
| 告警与呈现 | 将检测结果以可处置的告警形式提供给分析师 |

**场景举例**:某企业有 50 台服务器,攻击者对其中一台执行 SSH 弱密码爆破。若无 SIEM,安全人员需逐台服务器登录、分别查看各自的认证日志,才能拼出攻击全貌;部署 SIEM 后,所有认证失败日志被集中归一化到统一字段(`source.ip`/`user.name`),检测引擎识别出"同一源 IP 短时间多次认证失败",在数秒内生成一条暴力破解告警,并在看板上可视化攻击源 IP。

**与相邻系统类型的区分**:

| 系统类型 | 关注点 | 输出 | 典型工具 |
| --- | --- | --- | --- |
| 日志管理(ELK) | 日志可检索、可留存 | 日志索引与看板 | Elasticsearch + Kibana |
| 指标监控 | 系统指标是否正常 | 指标阈值告警 | Prometheus + Grafana |
| **SIEM** | **安全行为是否可疑** | **安全告警(规则/关联/评分)** | 本项目 |

**对本项目的定位**:Elastic Stack 承担了日志采集与存储(即 ELK 的部分),而 **Flink 检测引擎与告警模型才是 SIEM 的本质**——这是本项目与普通 ELK 日志平台的关键区别。

## 2. 数据在 SIEM 中的阶段与称谓(核心术语链)

安全数据从产生到被处置,经历五个阶段,每个阶段有固定的称谓:

```
日志 log → 事件 event → 检测命中 hit → 告警 alert → 案件 incident
```

| 阶段 | 定义 | 产生者 | 本项目落点 |
| --- | --- | --- | --- |
| **日志 (log)** | 设备输出的原始文本行,未经过任何处理 | 各类设备 | `Aug 1 10:20:00 server03 sshd[9999]: Failed password for test from 172.16.1.20` |
| **事件 (event)** | 原始日志经解析与字段标准化后的结构化记录 | Logstash | 写入 `siem-events-*` 的 JSON 文档 |
| **检测命中 (hit)** | 事件满足某条检测规则的条件,属于检测的中间结果 | Flink 规则引擎 | `Rule.getCondition().matches(...)` 返回 `true` |
| **告警 (alert)** | 命中后生成的、供分析师处置的通知记录 | Flink | 写入 `siem-alerts` 的 JSON 文档 |
| **案件 (incident)** | 一个或多个告警经归并后进入调查的处置单元 | Spring Boot `CaseService` / `CaseAggregateJob` | 案件状态和案件—告警关系由 PostgreSQL 管理；ES 保留兼容镜像并提供事件检索 |

**场景举例(完整术语链)**:攻击者对 `server03` 尝试 20 次 SSH 密码,产生 20 条认证失败**日志**;Logstash 将其解析为 20 条字段统一的**事件**;Flink 窗口规则识别出"5 分钟内 ≥5 次失败",产生一次**检测命中**;命中被渲染成一条暴力破解**告警**写入 `siem-alerts`;分析师确认后,该告警与后续相关告警被归并为一个**案件**展开调查。

**关键性质:一条日志被解析为事件后,可能命中多条规则,从而产生多条告警。**
场景举例:一条 `Failed password for test` 事件同时满足"SSH 认证失败"与"常见弱账号被爆破"两条规则 → 1 条事件产生 2 条告警。

## 3. 术语表

### 3.1 告警属性

| 术语 | 定义 | 示例 / 说明 |
| --- | --- | --- |
| **severity(严重级)** | 告警的静态严重等级,表示危险的粗略分档 | `info / low / medium / high / critical` 五档 |
| **risk_score(风险分)** | 数值化危险评分(0-100),可参与计算与排序,比 severity 更精细 | 设计稿中的 `alert.risk_score`,如暴力破解 73 分 |
| **rule_id / rule_name** | 命中规则的唯一标识与展示名 | `rule-ssh-auth-failure-001` / `SSH 认证失败` |

### 3.2 告警质量

| 术语 | 定义 | 场景举例 |
| --- | --- | --- |
| **True Positive (TP)** | 告警属实,确实存在攻击 | 攻击者确实在爆破,规则正确报警 |
| **False Positive (FP)** | 告警不实,实为正常行为(误报) | 运维人员连续输错密码,被规则报为爆破 |
| **False Negative (FN)** | 存在攻击但未产生告警(漏报) | 攻击成功登录,但没有规则覆盖该模式 |
| **FP rate(误报率)** | FP / (FP + TP),衡量告警中误报的占比 | 某规则一天告警 100 条,其中 30 条为误报 → FP rate = 30% |

**场景举例(误报与漏报的权衡)**:将暴力破解窗口从 5 分钟放宽到 30 分钟,能够捕获慢速爆破(降低 FN),但正常运维的偶发输错也可能落入窗口(升高 FP)。检测规则调参的本质就是在 FP 与 FN 之间取平衡。

### 3.3 检测手段

| 术语 | 定义 | 本项目对应 |
| --- | --- | --- |
| **归一化 (normalization)** | 将不同来源的字段统一为同一套命名与类型 | Logstash 将自定义字段转为 ECS 字段(`source.ip`) |
| **关联 (correlation)** | 组合多个事件或信号进行判断 | 时间窗口规则、CEP 攻击链规则 |
| **抑制 (suppression)** | 同一实体命中同一规则时,在时间窗内仅产出一条告警 | 设计稿 P0:keyed state + TTL |
| **去重 (dedup)** | 相同或等价的告警仅保留一条 | 与抑制配合使用 |
| **富化 (enrichment)** | 为事件补充外部上下文(地理位置、IP 信誉等) | 设计稿 P2:GeoIP |

### 3.4 时间语义

| 术语 | 定义 | 本项目 |
| --- | --- | --- |
| **事件时间 (event time)** | 安全事件实际发生的时间,即日志中记录的时间 | `@timestamp` |
| **摄入时间 (ingest time)** | 系统处理到该事件的时间 | `alert.created_at` |

**场景举例(时间语义错误的影响)**:日志因网络延迟 5 分钟才到达系统。若 `@timestamp` 取摄入时间,时间线整体后移,基于时间的窗口分析(如"5 分钟内失败次数")会被错误拆分,产生错误的检测结果。因此 `@timestamp` 必须采用事件时间。

### 3.5 组织与角色

| 术语 | 定义 |
| --- | --- |
| **SOC** | 安全运营中心(Security Operations Center),由安全分析师组成,负责安全监控与事件处置 |
| **SIEM** | 供 SOC 使用的检测与告警工具 |
| **SOAR** | 安全编排与自动化响应(Security Orchestration, Automation and Response),执行封禁、隔离等自动化处置 |
| **XDR** | 扩展检测响应(Extended Detection and Response),整合端点/网络/云等多源检测,是 SIEM 的演进方向之一 |

### 3.6 运营效率指标

| 术语 | 定义 |
| --- | --- |
| **MTTD** | 平均检测时间(Mean Time to Detect):从攻击发生到被系统发现 |
| **MTTA** | 平均确认时间(Mean Time to Acknowledge):从被发现到分析师确认 |
| **MTTR** | 平均修复时间(Mean Time to Respond):从确认到处置完成 |

## 4. 术语链与组件总览

```
日志 ──Logstash──> 事件 ──Flink──> 命中 ──> 告警 ──ES/Kibana──> 分析师
 (log)           (event)        (hit)       (alert)               │
                                     │                           ▼
                          命中哪条规则?                 CaseService + PostgreSQL
                          rule_id                              案件
```

## 5. 自测

1. 一条日志最多能产生几条告警?依据是什么?(可多条:命中几条规则就产生几条告警)
2. `@timestamp` 应取事件时间还是摄入时间?为什么?(事件时间,否则时间线后移、窗口分析被拆错)
3. FP rate 偏高说明什么?应该如何处理?(该规则误报多,应调参或退役)
4. SIEM 与 ELK 日志平台的区别是什么?(ELK 是存储检索底座,SIEM 增加检测引擎与告警治理)
